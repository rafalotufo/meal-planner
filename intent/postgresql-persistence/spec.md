## Schema and transactions

Preserve domain IDs as text, timestamps as exact epoch millisecond numbers (PostgreSQL bigint converted only within safe integer bounds), normalized-email checks, unique subject/email/token, required single family and restrictive foreign keys, invitation lifecycle checks and indexes. Archive original SQLite migration files as historical evidence; new PostgreSQL migrations live under drizzle/postgresql with their own journal. No automatic SQLite import or deletion.

All family mutations execute on a single checked-out connection in BEGIN/COMMIT with rollback and guaranteed release. Use a database-scoped transaction advisory lock shared by all family mutations before reading admission/recipient/membership/rate limits. This conservatively preserves SQLite’s single-writer ordering across server instances and transaction poolers while allowing concurrent reads. Use READ COMMITTED so admission reads occur after lock acquisition. Lock and statement timeouts bound contention; errors fail closed. Future higher-write scaling may narrow locks in separately reviewed work. Every request still rechecks current server-side admission. All external SQL values remain bound; no request-driven SQL identifiers.

Migration command uses a separate migration advisory lock and transactional DDL/history, checks exact ordered repository hash/timestamp prefix and complete catalog signature. Runtime checks full history and required schema without repair. Unknown/changed/partial schema fails closed. Catalog signature covers columns, defaults, constraints and indexes; committed expected signature comes from an isolated migrated test database. Migration failure rolls back ledger and schema. Rollback of this undeployed initial schema is documented and tested only on owned disposable databases; no destructive dev/production reset command.
