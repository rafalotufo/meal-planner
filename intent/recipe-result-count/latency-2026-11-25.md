# Recipe count latency experiment — 2026-11-25

Requested by Rafael to compare 6, 10, and 20 search results before deciding
whether to change the application. This is a local live-provider experiment;
no application setting, deployment, database, or workflow gate was changed.

## Method

Source checkout: `cd60db410ab28897f0d8e7ab54daa0b8821a6248`.
Provider source SHA-256:
`8824714a1f5783ec34f151c42e61694abea48df1c44d166b1eede30dc4f65899`.

Nine sequential live searches: `chilli`, `pizza`, and
`quick vegetarian weeknight dinner`, each requested at 6, 10, and 20 results.
Order rotated by query: 6/10/20, 10/20/6, 20/6/10.
Temporary provider copies replaced each instruction's `six` with the target
number and changed the validated-result cap from 6 to that number. No other
provider behavior changed. Credentials were read privately from `.env.local`.

All counts used GPT-6.2 Sol (`gpt-6.2-sol`), low reasoning, one Responses API
request, required live web search, eight maximum tool calls, 5,000 maximum output
tokens, 20,000 output characters, and a 60-second shared deadline. The existing
validator, grounding requirements, URL deduplication, and safe photo enricher
were reused. Photo discovery stayed capped at the first six recipes, two jobs
at once, and six seconds total. Results above six therefore do not get equal
photo-discovery coverage. Provider-supplied validated photo metadata is retained.

Wall-clock timing includes provider response processing and optional photo
work. Instrumentation additionally parses a cloned provider response to record
status, token usage, and web-search-call count; this small extra work is included
in the timings. The instrumentation clone does not enforce the application's
1 MiB reader bound, though the actual provider parser still does. No raw
provider response, source body, credential, or returned card is retained.

This isolates count changes under current budgets. It does not measure a
version with proportionally larger research/output budgets or photo coverage.
These are local provider-plus-photo timings, excluding HTTP routing, family/
admission checks, notebook persistence, browser rendering, and hosted latency.
One trial per query/count is exploratory evidence, not a repeat-run variance,
p95, or reliability estimate. Structural validation is not an independent
source-page quality or dietary-constraint audit. Timeouts may still incur usage;
missing timeout token metadata cannot be interpreted as zero cost.

## Results

| Query | Request 6 | Request 10 | Request 20 |
|---|---:|---:|---:|
| chilli | 45.7 s; 6 recipes | 44.4 s; 10 recipes | 60.0 s; timeout |
| pizza | 36.4 s; 6 recipes | 56.0 s; 8 recipes | 60.0 s; timeout |
| quick vegetarian weeknight dinner | 30.2 s; 5 recipes | 43.2 s; 5 recipes | 54.8 s; 8 recipes |

- Request 6: 3/3 completed; median 36.4 s, range 30.2–45.7 s;
  returned 6, 6, and 5 recipes. Target count reached in 2/3 trials.
- Request 10: 3/3 completed; median 44.4 s, range 43.2–56.0 s;
  returned 10, 8, and 5 recipes. Target count reached in 1/3 trials.
  Median was 22% (7.9 s) higher than the six-result trials.
- Request 20: 1/3 completed, returning 8 recipes in 54.8 s; two requests
  timed out at 60.0 s. Target count reached in 0/3 trials. Timeouts are
  failures, not successful 60-second responses or zero-result searches.

The paired count-10 versus count-6 time differences were −1.3 s (chilli),
+19.6 s (pizza), and +13.0 s (dinner). Additional validated recipes were
+4, +2, and 0 respectively. Different queries, source selection and provider
variability prevent attributing every millisecond solely to count.

## Decision support

Keep six for now under current budgets. Ten produced additional choices for
two queries, but added substantial time for pizza and dinner and reached ten
only once. Twenty is unsuitable as a count-only change under the current
60-second deadline. This is an exploratory recommendation, not a statistical
claim that ten always costs 22% more time or that twenty can never work.

If more choices are still desired, a follow-up can test ten across repeated
representative queries and independently audit result quality before a product
change. Increasing research/output budgets or enriching every additional photo
would be a separate experiment with different latency and usage characteristics.
The application remains capped at six; no release is requested or performed.
